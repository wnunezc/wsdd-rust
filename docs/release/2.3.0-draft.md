# WSDD 2.3.0

Changes since the published 2.2.0 release.

## MySQL Core

- Replaces the single MySQL process with two MySQL 26.7.0 instances in the existing `WSDD-MySql-Server` container: an ephemeral Linux-filesystem primary and a persistent replica using the existing Windows NTFS bind mount. The container name, `wsdd-core/database` service, host port `127.0.0.1:3306`, Docker network and phpMyAdmin connection remain the same.
- Adds replication and recovery checks before the primary accepts writes. Docker → MySQL Core now provides Deploy, Validate and Recreate with deployment stages and a copyable operation log. Recreate waits for the replica, replaces only the MySQL container and checks restored SQL state before reporting success.
- Adds guards against starting a legacy MySQL image on a converted datadir. Full environment backup requires a clean MySQL stop; the existing full restore action refuses this replicated layout before changing containers or data, because its file overlay is not an atomic restore.
- Includes the isolated `WSDD-MySql-Server-Test` experiment and its manual Deploy, Validate and Recreate actions. It does not replace or automatically deploy the Core service.

## Existing data and storage

- **Existing MySQL datadirs are not converted by the MSI.** The new Core requires `lower_case_table_names=1`; a datadir initialized with `2` requires a separately verified logical migration and a preserved backup before using this layout. Do not delete or overwrite an existing `bin/mysql/data` directory to force startup.
- The developer's local datadir conversion and its backup are not included in the installer or repository. A fresh installation can initialize an empty datadir.
- The persistent replica is an operational copy, not an independent backup. Logical mistakes and deletes replicate too. VirtioFS is **not enabled** by this release; the NTFS bind remains in use. Future VirtioFS compatibility and its performance require separate validation.

## Validation and known limits

- The locally installed test MSI started the Core healthy with the existing converted data. Both instances retained 14 user schemas and 1,771 tables. SQL Validate passed before and after a 51.2 MB load; the user ran Recreate from WSDD and the restored SQL hash matched. The replica caught up after the load without replication errors.
- Three local rounds measured a 1.770 s median for the primary's 51.2 MB bulk insert, versus 14.274 s in an earlier single-instance run. The earlier SQL generator was not preserved, so these are **not controlled, identical benchmarks** and do not isolate filesystem effects. The 500 individual commits were slower in the new run (3.708 s versus 3.271 s). See the [technical report](https://github.com/wnunezc/wsdd-rust/blob/v2.3.0/docs/maintenance/mysql-core-replicated-datadir-cutover-2026-10-20.md).
- Normal stop/start of the production Core and an existing PHP application's database workflow have not yet been manually verified. The full restore action remains unavailable for this layout. These limits were disclosed when the stable release was chosen.
